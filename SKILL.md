# Holytail meaning gate

Preserve meaning first; minimize the mechanism second.

Holytail is the gate in front of Ponytail-style economy, not a competing
optimization mode. During open exploration, do not use either lens to close
framings, architectures, or product decisions. When work moves to
implementation, preserve the meaning already established by the user's current
request and accepted project instructions, then minimize only the mechanism.

## Default inline path

For clear work, perform this check inline without stopping the task:

1. Derive the protected meaning from the current request and applicable project
   instructions. Do not require the user to restate what is already clear.
2. Name only distinctions materially at risk. Treat all other architecture,
   data representation, dependencies, and implementation shape as experimental
   space unless the user constrained them.
3. Apply the Ponytail ladder only inside that space: no mechanism, reuse,
   standard library, native primitive, installed dependency, then the smallest
   cohesive local mechanism.
4. Verify the protected behavior in proportion to its risk. Do not require a
   separate contract document, Holytail subagent, or semantic reviewer merely
   because code is being changed.

An internal semantic brief can be one sentence or a few bullets. Do not emit it
unless it helps the user understand a real trade-off.

## Formal escalation path

Escalate when implementation follows substantial product or architecture
exploration, or when a shortcut could collapse a material distinction in
authority, lifecycle, evidence strength, security, persistence, compatibility,
or decision ownership. Also escalate when the user explicitly requests the
formal workflow.

On escalation:

1. Read [references/semantic-contract.md](references/semantic-contract.md) and
   compile only the relevant accepted meaning, protected distinctions,
   invariants, non-goals, and genuinely open decisions. The current user request
   or accepted project record may already constitute acceptance; ask again only
   for a blocking ambiguity or a meaning-changing choice.
2. Use a separate `holytail` worker only when bounded execution would materially
   reduce context contamination or clarify ownership. Give it the compact brief,
   exact task boundary, relevant source and tests, constraints, evidence, and
   non-goals—not the exploratory transcript.
3. Require [references/delivery.md](references/delivery.md) only for the formal
   route, proportionate to the material claims.
4. Use a fresh `semanticreviewer` with
   [references/review.md](references/review.md) only when independent review can
   materially change acceptance. Otherwise use focused tests or direct review.
5. Return failed invariants as targeted rework with an evidence delta. Return
   genuine product ambiguity to the user; do not loop automatically.

One compact brief, one implementation pass, and the smallest decisive evidence
set are the default. Formality grows with semantic risk, not task size.

In a project already configured for Soulmate, use its exact workflow, declared
boundaries, profiles, and memory rights to record the worker, reviewer, and
lead outcomes. Do not invent a second orchestration schema or change persisted
formats. Without a configured Soulmate project, do not initialize or mutate
project control state without request.
