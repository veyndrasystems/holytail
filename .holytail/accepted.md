## Problem

An implementation minimizer may preserve broad protected categories while
silently dropping behavior accepted for one task. Holytail must make that
task-specific meaning reviewable before minimization and check it afterward
without competing with the minimizer.

## Accepted implementation increment

1. Position Holytail around an already-active minimizer.
2. Keep Ponytail enabled and treat it as the reference minimizer.
3. Provide a standalone accepted-meaning artifact and a visible post-check
   artifact when Soulmate is absent.
4. Preserve Soulmate as the authority, evidence owner, and final acceptor when
   it is present; Holytail does not initialize it or create a competing record.
5. Make native Codex repository-marketplace installation primary and keep
   dotagents as an optional path.
6. Remove Holytail economy behavior and economy positioning.
7. Guard Ponytail intensity names from assigning Holytail quality or route
   axes without explicit authorized policy.
8. Keep public documentation honest about evidence strength, enforcement, and
   benchmark coverage.

## Protected distinctions

| A | B | Required distinction |
| --- | --- | --- |
| Ponytail `full` | Holytail `FULL` | Minimizer intensity cannot assign execution quality |
| Ponytail `ultra` | Holytail route or escalation | Minimizer intensity cannot assign routing |
| `hook_observed` | verification | A banner proves only that the hook ran |
| `agent_declared` | independent verification | An assertion is not objective evidence |
| Authored source | generated projections | Generated host files remain disposable |
| Hook order | authority | Co-running hooks do not assign precedence |
| Portable instructions | runtime enforcement | Enforcement is claimed only where observed |
| Standalone artifacts | Soulmate authority | The fallback is not a competing run format |

## Invariants and negative requirements

- I1: Holytail contains no minimization ladder or minimization behavior.
- I2: Ponytail remains active and is not treated as conflicting state.
- I3: No Ponytail banner or intensity assigns a Holytail axis.
- I4: An unassigned quality mode remains `MODE-UNBOUND`.
- I5: `full` and `FULL` remain distinct values on distinct axes.
- I6: `ultra` is not a Holytail route, mode, or escalation trigger.
- I7: `.holytail/accepted.md` is read before minimization when Soulmate is
  absent.
- I8: `.holytail/check.md` is produced after implementation when Soulmate is
  absent.
- I9: The post-check identifies both the accepted artifact and implementation
  snapshot and reports invariant-level findings.
- I10: Soulmate remains authority and final acceptor when present.
- I11: Holytail does not initialize Soulmate or create a competing run format.
- I12: Holytail does not mutate third-party plugin state.
- I13: Hook order does not imply authority or precedence.
- I14: `hook_observed` and `agent_declared` are not reported as verification.
- I15: README copy does not claim measured preservation until a reproducible
  result exists.
- I16: Publicly tracked artifacts contain no machine-local home paths, private
  operator identifiers, or internal execution-routing notes.

## Observable success

- The validator rejects economy behavior and Ponytail-to-Holytail axis
  collisions.
- The validator rejects machine-local paths in public Holytail artifacts.
- Native Codex marketplace installation, listing, hook execution, and removal
  succeed in an isolated environment.
- The standalone post-check binds to this file and names each protected
  invariant it evaluated.
- Documentation includes installation, uninstall, enforcement limits, and
  benchmark caveats without stale prose pins.

## Implementation boundary

- Observable files: repository-authored source, tests, documentation, plugin
  metadata, and standalone Holytail artifacts.
- Writable files: repository-authored files required by this increment.
- Permitted external effects: explicitly authorized repository publication and
  deployment synchronization.
- Forbidden effects: third-party plugin mutation, new host coverage, Soulmate
  feature work, hosted services, dashboards, or unrelated scope expansion.
- Dependency policy: add no dependency for validation that the standard
  library can perform.

## Compatibility and operations

- Existing evidence labels and their limits remain unchanged.
- Generated `.agents/`, `.codex/`, and `.claude/` projections are not authored
  Holytail state.
- Read-only reviewer enforcement is reported per host and only where the host
  actually supplies it.
- Exact third-party versions belong in load-bearing tests, not general prose.
- Releases are immutable once published; release creation remains a separate
  maintainer action.

## Security and privacy boundary

- Public artifacts describe product meaning and observable evidence, not local
  filesystem layout or private execution logistics.
- Authentication and publication authority remain with the repository
  operator.
- Holytail grants itself no memory, account, plugin, or repository rights.

## Explicit non-goals

- Adding hosts
- Soulmate feature development
- Monetization or hosted services
- Expanding the benchmark claim before real evaluation data exists
- Rewriting routing logic beyond the required axis-collision guard

## Reviewer obligation

Independent review is required for the public privacy boundary and the
Ponytail/Holytail axis distinction. Decisive evidence is a clean tracked-tree
scan, validator mutation coverage, isolated installation evidence, and a
reachable-history identity check.

## Expected semantic remainder

- Real-model benchmark execution and publication of measured results
- Release tag and GitHub Release creation under maintainer authorization

## Formal acceptance gate

The increment is acceptable only when every blocking invariant above is
represented in authored source, exercised by the smallest decisive checks, and
reported without promoting hook or agent assertions into verification.
