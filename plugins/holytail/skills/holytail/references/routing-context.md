# Holytail routing context

This hook presents routing; it does not prove that Holytail is active or that
the implementation is semantically compliant.

Holytail performs no minimization. It freezes task-specific accepted meaning
before the user's already-active minimizer runs and checks the implementation
afterward. Ponytail remains active and is bracketed by this workflow.

- Leave open exploration open. Do not use implementation choices to settle
  product meaning, scope, framing, or architecture.
- Before an implementation action, choose `INLINE` for clear low-risk work or
  `FORMAL` when a deterministic escalation trigger applies. A configured
  Soulmate workflow overrides this heuristic.
- Begin every user-visible response while Holytail is active with one line:
  `Holytail :<FULL|ECO|MODE-UNBOUND> · <INLINE|FORMAL> ·
  evidence=agent_declared`.
- `FULL` and `ECO` are Holytail quality modes; `INLINE` and `FORMAL` are
  Holytail routes. Ponytail `lite`, `full`, `ultra`, and `off`, plus any
  Ponytail banner or intensity, are unrelated and cannot assign either axis or
  trigger escalation. `full` is not `FULL`; `ultra` is not a Holytail signal.
  Only an explicit authorized project policy may define a mapping. Formal work
  requires an assigned `FULL` mode; if no quality mode is available, report
  `MODE-UNBOUND` rather than guessing. `Quality mode: FULL` in the exact
  assignment is sufficient. A host `reasoningEffort` such as Codex `ultra` supplies it only
  when an authorized project policy explicitly defines that mapping.
- `INLINE` preserves accepted meaning and verified existing contracts while
  the active implementation workflow chooses mechanism. `FORMAL` freezes an
  immutable semantic contract, uses a bounded worker, and adds a fresh reviewer
  when decisive.
- Escalate for persisted schemas or migrations; public API or compatibility;
  authentication, authority, permissions, memory rights, or trust boundaries;
  deletion or external/irreversible effects; lifecycle-state collapse;
  raw-evidence replacement; or the first implementation after meaning-rich
  exploration.
- Keep Ponytail active and unchanged. Hook order is not authority, and
  co-running hooks do not assign precedence.
- Worker completion, reviewer approval, Soulmate lead acceptance, and objective
  truth remain distinct. Never claim stronger evidence than was observed.

Without Soulmate, read `.holytail/accepted.md` before implementation and write
`.holytail/check.md` after it with accepted-artifact and implementation-snapshot
identities plus invariant-level findings. With Soulmate, it remains authority,
evidence owner, and final acceptor; do not initialize it or create a second run
format.

`hook_observed` means only that this hook ran. `agent_declared` is assertion,
not verification. Codex read-only enforcement exists only when its native
reviewer profile is used; portable instructions are not enforcement. Holytail
never mutates third-party plugin state.
